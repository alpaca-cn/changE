feat(task10): HTTP 骨架 + 端口协商（stdout 上报 CHANGE_PORT=）

外壳要发起请求就得知道后端监听在哪个端口，而 `server.port: 0` 意味着端口是运行时才知道的。
本任务把这条信道定下来：后端在 `ApplicationReadyEvent` 时把实际端口以固定格式打到 stdout，
外壳是子进程的父进程，按前缀读一行即可——不写文件，省掉了文件路径与「崩溃残留端口文件
误导下一次启动」的清理时机问题。

新增 PortReporter（上报端口）、HealthController（只读 GET /api/health）、
CacheConfig（CacheStatus 占位实现，Task 11 换成 Redis / NoOp 二选一）。

## A. 生产形态实测 —— `local.server.port` 真的可用

任务书要求不能假定，所以从 `%TEMP%\change-t10-probe`（项目目录之外，模拟外壳）起
`java -jar change-backend-0.1.0-SNAPSHOT.jar`，stdout / stderr 分别重定向到两个文件
（脚本 `_review/t10_probe.py`）：

- **① stdout 上确实出现了协议行**：`CHANGE_PORT=56934`，启动后约 **5.2 s** 出现。
  属性在 `ApplicationReadyEvent` 时机有值，不需要换成更早的 `WebServerInitializedEvent`。
- **② 那个端口确实能访问**：
  `GET http://127.0.0.1:56934/api/health` → `200`，
  body = `{"cache":"disabled(placeholder)","status":"up"}`
- **③ 监听地址是 127.0.0.1，不是 `::` / `0.0.0.0`**：
  `netstat -ano` → `TCP    127.0.0.1:56934        0.0.0.0:0              LISTENING       45536`
  `Get-NetTCPConnection -OwningProcess 45536 -State Listen` → LocalAddress `127.0.0.1`
  另从本机非回环地址（例如 10.105.209.20）连接**一律 ConnectionRefused**，
  证明 `server.address: 127.0.0.1` 真的生效、没有顺带监听所有网卡。

**④ 那行是不是恰好一行、没有多余输出干扰？** 是，实测：

- stdout 47 行，其中 `CHANGE_PORT=` 前缀行 **恰好 1 行**、含 `CHANGE_PORT` 的行也是 1 行；
- **Spring Boot 的日志走 stdout**（39 行 INFO 全在 stdout），
  **stderr 上只有 8 行 JVM WARNING**（`A restricted method in java.lang.System`、
  `sun.misc.Unsafe::allocateMemory`），stderr 里 INFO 数 = 0；
- 该行**没有任何日志前缀**（不是 `... INFO ... CHANGE_PORT=`），外壳按前缀匹配安全。

> ⚠️ 实测发现的坑（已写进计划，给外壳实现）：Windows 上 `System.out.println` 写的是 `\r\n`，
> 该行**原始字节是 `b'CHANGE_PORT=56934\r'`（18 字节，不是 17）**。外壳必须按行读取并 trim
> （Rust 的 `BufRead::lines()` 会去掉 `\r`），不要只按 `\n` 切；否则后缀是 `"56934\r"`，
> `parse::<u16>()` 会报错。Java 的 `Integer.parseInt` 恰好容忍尾部 `\r`，别被它骗过。

## D. 变异测试实测（不是纸面推断）

| 变异体 | 结果 |
| --- | --- |
| `PREFIX` → `CHANGE_PORTX=` | 红（`port_reporter_...:40`） |
| JSON 键 `status` → `statusx` | 红（`health_...:32`） |
| JSON 值 `"up"` → `"down"` | 红（`health_...:32`） |
| JSON 键 `cache` → `cachex` | 红（`health_...:33`） |
| `port > 0` → `port > 65535` | 红（`random_port_...:25`） |
| 去掉 `RANDOM_PORT`（单类） | 红（3 个 ERROR：`@LocalServerPort` 注入失败） |
| 去掉 `RANDOM_PORT`（全量） | 红（`Tests run: 105, Failures: 0, Errors: 3`） |
| 对照：注释里加一个空格 | **绿**（预期如此——证明工具不会误报红） |
| `cache` 的值改成空串 `""` | **绿（没抓住）** |
| `cache` 的值改成假状态 | **绿（没抓住）** |
| 删掉 `cacheStatus()` bean | 红（上下文起不来） |

**最弱的一条**是 `assertThat(r.getBody()).contains("\"cache\"")`：它只查**键名**是 JSON 里
的一个子串，不查值。上表最后两个变异体证明——`"cache":""` 和 `"cache":"缓存：已连接
1.2.3.4:6379"` 都能全绿通过，也就是「缓存状态」这个字段的值可以完全错而测试不知道。
它是三条测试里唯一一条能被「实现给出错误数据」杀不掉的断言。本轮不改（Task 11 会把
`CacheStatus` 换成真实现，届时该补一条查值的断言），但把结论记在这里。

**`random_port_was_assigned` 是不是恒真？不是。** 判断依据是实测而不是推理：
`@LocalServerPort` 注入失败时字段确实是 0，但那时测试**根本跑不到断言**——
把 `webEnvironment` 去掉后 3 个测试全部是 `BeanCreation ... Injection of autowired
dependencies failed`（ERROR 而不是 Failure），`failIfNoWebServer` 这个机制让
「没有 web 环境」表现为上下文起不来。所以 `isGreaterThan(0)` 只能被「真的分到了 0 或负数
的端口」杀掉——变异体 `> 65535` 变红证明这行确实在执行、不是被跳过的恒真语句。
它仍然是三条里较弱的一条（断言强度低），但**不是恒真**。
