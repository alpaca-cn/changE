## 一、这个项目要解决什么

市面上的健身 App 都是商业订阅制，槽点几乎全部源自「多租户」这件事本身：功能被订阅墙切碎、有广告、数据导出受限、食物库偏西式包装食品、训练计划是静态模板而非按个人历史递进。

**change 的前提是：只有一个用户。** 因此不需要 `user_id`、不需要权限体系、不需要计费、不需要为「照顾所有人体型」而牺牲精度。所有设计取舍都服从这一条。

**名字的含义**：改变。

### 明确不做

| 不做 | 理由 |
|---|---|
| **多用户 / 账号 / 权限 / 社交 / 排行榜** | **不在本阶段，但路径不堵死**。用户已明确：若自用感觉不错，可能推广给朋友——那属于**另一个产品形态**（需要服务端、托管、鉴权与移动端），不是加个 `user_id` 就完事。现在就为它做重准备会付出很大代价且大概率猜错；但有三件便宜的保险值得先做，见下节 |
| 云同步 / 服务端部署 | 数据全在本机；备份 = 复制一个文件 |
| **手机 App（iOS/Android）** | **不在本阶段，但用户已明确：桌面版做出来后可能再做移动端**。因此界面按响应式写，不做只适配宽屏的布局；业务逻辑全部放在 Java 后台而不是前端，将来换壳代价最小 |
| 微信小程序 | 注册审核流程长，自用无必要 |
| 计划模板（Routine） | 第一版不做；`WorkoutSession.source_routine_day_id` 已预留可空外键，将来加不返工 |
| 食物库编辑后台 | 不做管理界面；直接改数据即可，手工补 20–50 条常吃项。录入侧另有「外卖订单录入」一条路径，见下 |
| 商业化 | 见第七章许可证一节：Z-Anatomy 的 ShareAlike 与部分 NC 部件本就限制商用 |

### 多用户：现在不做，但不把路堵死

用户的使用感觉若不错，可能推广给朋友。**单用户桌面版 → 多用户社交版不是增量改造，而是另一个产品**：需要服务端、托管、鉴权、移动端，以及一个真实的数据库服务器。

现在就为它做重准备会付出很大代价，而且大概率猜错。**但有四件便宜的保险值得先做**：

| 保险 | 成本 | 收益 |
|---|---|---|
| 数据访问层走 ORM（JPA / MyBatis），不写死数据库方言 | 低（本来就这么写） | 换 SQLite → MySQL 变成改配置 |
| 数据库迁移用 Flyway 管起来 | 低（本来就要做） | schema 演进有版本可循，多人版可复用 |
| 照片存储抽成一个接口（本地实现 / 将来的对象存储实现） | 低 | 上服务端时只加一个实现类 |
| 业务逻辑全部放 Java 后台，不在前端写 | 中 | 将来做移动端只需换壳；这也是「手机 App 后续可能做」的同一条保险 |

**明确不做**：现在就在表里加 `user_id`。那是把一个不存在的需求固化进 schema，将来真做多用户时该改的还是要改。

### 外卖订单录入：不直连平台，走截图与文本

用户希望能把美团、淘宝闪购上的外卖记录录进来。**先说不行的部分**：

- 美团开放平台、淘宝闪购服务商平台的接口面向的是**商家与服务商**，需要资质与授权协议，**没有面向个人用户的订单历史 API**。
- 爬虫抓取个人订单**违反平台条款**，且需要登录态与对抗风控，不做。

**能做且好用的两条路**（都不需要任何平台授权）：

| 路径 | 用户操作 | 系统处理 |
|---|---|---|
| **截图识别** | 在外卖 App 里截订单页，拖进 change | 多模态模型读出「店名 + 菜名 + 价格」→ 匹配食物库 → 出条目草稿 |
| **粘贴文本** | 复制订单文本，粘进智能体对话 | 智能体解析 → 出条目草稿 |

**关键设计判断：把它当成「一种录入方式」，不是「一个数据源」。**

外卖菜名（如「黄焖鸡米饭（大份）」）不会正好命中食物库，因此走的是与拍照识别**完全相同**的模式：**AI 出草稿 → 用户确认或修正 → 入库**。它复用已有的多模态识别、工具调用与 `MealItem` 结构，不需要新的数据表。

顺带一个副产品：订单里带着**店名与价格**，可以存进 `Meal.note`，用来回顾「这周点了几次外卖」——但那属于后续的统计功能，不进第一版。

### 借鉴与取舍：openGym

调研中发现 GitHub 上的 [openGym](https://github.com/DuarteSantos8/openGym)（10.9k star，AGPL-3.0，自托管健身追踪）与本项目目标高度重合。**注意：它是 AGPL-3.0，只可读思路、不可抄代码。** 逐项评估后的取舍如下。

**采纳（5 项）**

| 项 | 为什么值得抄 |
|---|---|
| **肌肉图三种模式**（容量 / 恢复中 / 长期未练） | 「长期未练」直接实现用户「看出哪里练得少」的诉求；三模式共用一份数据，只换着色函数 |
| **计时动作与每侧计数** | 平板支撑按秒、弓步按每侧——原来的 `repetitions` 字段表达不了，这是**数据模型的真实缺陷**，必须修 |
| **超级组分组** | `SessionExercise.superset_group` 一个可空字段即可表达 |
| **片重计算** | 知道你有什么片子，直接告诉你每边挂多少。自包含、成本低，健身房里真用得上 |
| **训练中即时 PR 提示** | 破纪录当场告诉他——数据已经在手，只是多一次比较，却是坚持下去最直接的动力 |

**采纳为设计原则（2 项）**

1. **历史可编辑，且衍生指标必须重算。** openGym 的做法是「记录从修正后的历史重新读取」。本项目的对应要求：编辑任何一次历史训练后，PR、进步曲线、周容量都必须跟着变——**这正是「写入即失效」这条缓存规则要覆盖的场景**。
2. **用户主动发起的改动可直接执行（可回退）；系统主动建议的改动必须显式确认。** 前者是「你说什么我做什么」，后者是「我建议你改」。风险不同，规则也该不同。

**列为后续可选（1 项）**

- **从 FitNotes / Strong / Hevy 导入**。价值真实（免去从零开始），但要写 CSV 解析与字段映射，属于独立工作量，不进第一版。

**明确不采纳（4 项）**

| 不采纳 | 理由 |
|---|---|
| Passkey / 多档案 / 跨设备同步 | 与本项目「单用户桌面客户端」的立论直接冲突 |
| 5,600+ 动作库 | 我们已有 876 个动作 + 中文名与说明。**多不是好，准才是** |
| 19 种语言 | 只需要中文 |
| 渐进规则引擎（Greyskull / 双重重渐进 / 三重重渐进） | 真有价值，但是一整个子系统，且每条规则都需要严格核对出处。列为将来可选 |

## 三、核心决定（已封板）

### 决定 1 · 产品形态 = 桌面客户端

**Tauri 2 外壳 + Vue 3 前端 + Java 后台**，本地 HTTP 通信。有独立窗口，无地址栏、无标签页。

参考物是用户提供的「B站工具箱」：Tauri 2 壳 + Vue 3 前端 + Python 后台。本项目把 Python 换成 Java，其余层照搬。

### 决定 2 · 「打卡」= 训练日志

数据结构 **训练 → 动作 → 组**。两条关键设计：

1. **目标值与实际值放在同一条组记录上**。「今天卧推该做 60×8、实际做了 62.5×6」是同一行数据，不需要两张表对账。
2. **用「组类型」枚举而不是「第几组」**。热身组、递减组、力竭组的语义完全不同，只记序号会丢信息。

### 决定 3 · 饮食记录 = 条目化 + 食物库

数据结构 **餐 → 条目 → 食物 + 份量**。一条硬性约束：

> **营养值一律按每 100 克存，份量单独存，热量永远实时算。**
> 热量 = `份量数值 × 换算克数 / 100 × 每百克营养值`
> **条目里绝不存绝对热量。**

反例：若 `MealItem` 里直接存 `174 kcal`，用户把份量改成 1.5 碗时得记得回去重算——漏一次账就永远对不上。

用户明确定位：**不需要太精准，大致热量即可。精度不是目标，可修正是。**

### 决定 4 · 智能体 = 可读也能写

它能看到训练、饮食、身体数据并回答；**也能改数据**——用户说「中午吃了两个包子一碗粥」→ 直接建条目；说「那个鸡腿其实是炸的」→ 改条目并重算。**说话就是录入。**

技术上即 **tool calling**，这正是用户「Java + agent」学习方向的核心。

**安全线（不可协商）**：

- 工具集是**白名单**，不是让模型自由写 SQL。
- 只允许 **新增** 与 **修改**，**不允许删除**。
- 每次改动写一条 `ChangeLog`，记录改动前/后快照，支持一键回退。

### 决定 5 · 人体图 = 3D，排在第二阶段，但界面位第一阶段就冻结

用户选定的角色是 **训练均衡度仪表盘**：肌肉按「本周训练组数」着色，一眼看出哪里练多、哪里漏练；点击某块肌肉 → 该肌群动作列表 + 加入训练。

**热力图算法**：

> 每记一组，该动作的 **主要肌群 +1**、**次要肌群各 +0.5**，按自然周（周一起算）汇总。

次要肌群算半分是训练量统计的通行做法：卧推对三头肌确实有刺激，但不该和臂屈伸算成一样的量。

**同一张肌肉图，三种查看模式**（借鉴自 openGym）：

| 模式 | 回答的问题 | 着色依据 |
|---|---|---|
| **容量** | 我这周练了多少 | 本周累计组数 |
| **恢复中** | 今天该练哪里 | 距上次训练的天数 + 该次训练量 |
| **长期未练** | 我是不是一直漏了某块 | 距上次被训练超过 N 天的肌群 |

三种模式共用同一份数据与同一张肌群映射表，只是着色函数不同。**「长期未练」这一种，正是用户原话里「看出哪里练得少」的最直接实现**——比单纯的周容量更能暴露「三个月没练过腿」这类问题。

**界面位冻结清单**（第一阶段完成，第二阶段只换渲染层）：

| 第一阶段做完并冻结 | 第二阶段改动 |
|---|---|
| 侧边导航「人体图」项 + 路由 `/body-map` | — |
| 最终布局：画布区 + 右侧面板 | — |
| 后端 `GET /api/body-map/volume` | — |
| 肌群映射表（683 对象名 ↔ 40–70 块肌肉 ↔ 肌群表） | — |
| `<BodyMap />` 组件契约：`volumeByMuscle` 入、`@muscle-click` 出 | — |
| 右侧面板（动作列表、容量进度） | — |
| 画布区内部：**SVG 静态热力图** | 换成 **Three.js 渲染** |

这样排的额外好处：2D 与 3D 共用同一张映射表、同一个接口、同一份数据。映射表是全流程唯一无法回避的纯手工活，放第一阶段能被真实数据提前检验。

### 决定 6 · 动作库数据源 = 三家各取所长

| 用途 | 来源 | 许可证 |
|---|---|---|
| 动作库主体（876 条、17 值固定肌群枚举、自带 1,746 张起止姿势图） | `yuhonas/free-exercise-db` | **Unlicense（公有领域）** |
| 中文说明补充 | `hasaneyldrm/exercises-dataset` 的 `instructions.zh` | **MIT（文本部分）** |
| 人体图区域路径（第一阶段 2D） | `vulovix/body-muscles` 的两个数据文件（约 24 KB，vendor 进项目） | Apache-2.0 |
| 3D 模型（第二阶段） | Z-Anatomy `MuscularSystem` + 低模皮肤壳 | **CC BY-SA 4.0（ShareAlike）** |

**中文动作名必须自己产出**：三个数据集都只有英文名（hasaneyldrm 也只有中文*说明*）。方案：用智能体批量翻译 876 条 + 拿 hasaneyldrm 的 1,324 条中文说明按动作名匹配做交叉校验。

**明确不能用**：hasaneyldrm 的 `images/` 与 `videos/` 版权属 Gym visual，仓库原文写明「克隆本仓库不等于获得媒体授权」，且限定 180×180、必须署名。

## 四、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 桌面外壳 | **Tauri 2 + Rust** | 安装包约 10 MB（实测产物 12 MB）；与参考项目同构 |
| 界面 | **Vue 3 + TypeScript + Vite + Pinia + Vue Router** | 与参考项目同构，生态成熟 |
| 业务后台 | **JDK 25 + Spring Boot 3.x + Maven 3.9.4** | 用户学习方向 |
| 智能体 | **LangChain4j + DeepSeek（OpenAI 兼容端点）** | 纯 Java 库；tool calling / 结构化输出 / SSE 流式齐全 |
| 数据库 | **SQLite 单文件**（详见下方「数据库怎么选」） | 免运维；备份 = 复制一个文件 |
| 数据库迁移 | **Flyway** | schema 必然演进，第一版就上迁移工具，避免手改表 |
| 缓存 | **Redis（可选，非必需）** | 用户决定要用它做缓存。设计成「有则用、无则退化为直连」，见下方「Redis 怎么用」 |
| 图片存储 | **本地文件系统** | 隐私优先；库里只存相对路径 + SHA-256 |
| 前后端通信 | **本地 HTTP，127.0.0.1 随机端口** | 比 stdio JSON 管道简单；调试可直接用浏览器看接口 |
| Excel 导出 | **Apache POI** | Java 版，对应参考项目的 openpyxl |

**明确排除**：

- **Semantic Kernel Java** —— Java 分支已废弃，微软主线转 Agent Framework（仅 .NET / Python / Go）。
- **Spring Boot 4 / Spring AI 2.x** —— 建在 Spring Framework 7 上，与 Boot 3.x 线分叉。
- **Google ADK for Java** —— 偏 Gemini、RAG 弱；留作第二阶段学习目标。
- **Electron** —— 零工具链但安装包 150 MB 起；用户选了 Tauri。
- **JavaFX 纯 Java 客户端** —— 界面工作量大数倍，会把时间从「Java + agent」挪到「手写界面」。
- **直接用 `FBXLoader` 加载 FBX** —— 实测必须转 GLB：35.6 MB → 4.71 MB。
- **保留 683 个独立 mesh 渲染** —— draw call 是性能瓶颈，必须合并几何。

### 数据库怎么选（回答「MySQL 还是 Redis」）

先把问题拆开：**MySQL 和 Redis 不是二选一的关系。** Redis 是内存缓存与数据结构存储，不是关系型数据库的替代品。真正是两个独立的问题。

#### 问题一：关系库用 SQLite 还是 MySQL

**结论：主库用 SQLite，但提供 MySQL profile 供练习与将来切换。**

| | SQLite | MySQL |
|---|---|---|
| 部署 | **零运维**，一个文件随程序走 | 要装服务、建账号、配端口、管密码 |
| 备份 | 复制一个文件 | `mysqldump` |
| 适合 | **单用户桌面应用** | 多人、并发写、服务端 |

**关于「能不能用上我学过的 Java 知识」——可以，而且几乎全部。**

SQL 语法、建表与索引、事务、连接池（HikariCP）、JDBC、Spring Data JPA、MyBatis，这些**在 SQLite 上完全一样**。差别只有三处：驱动（`sqlite-jdbc` vs `mysql-connector-j`）、连接 URL、以及 Hibernate 的方言（SQLite 需要 `hibernate-community-dialects`）。

**具体做法**：数据访问层照常用 JPA / MyBatis 写，数据库连接做成配置项，另外提供一份 `application-mysql.yml`。想练 MySQL 时，本地装一个 MySQL，切 profile 就能用**同一套代码、同一套 Flyway 迁移脚本**跑起来。日常自用则不必背 MySQL 的运维。

> 这样安排的理由：桌面客户端的第一体验是「双击就能用」。让它依赖一个必须常驻的数据库服务，是把运维负担转嫁给自己——而这个负担换不来任何功能。

#### 问题二：Redis 怎么用

**用户决定：要用，做缓存。** 以下是按这个决定做的设计。

**先把实话说了**：在单人桌面版里缓存一个本地 SQLite 文件，**几乎没有性能收益**——本地读文件通常比走一次 TCP 到 Redis 还快。所以这件事的价值不在「让 App 变快」，而在**练习一套正确的缓存工程模式**。既然目的是学习，就该按正确的方式学，而不是把 Redis 当成一个「我用了」的摆设。

**因此设计成：可选、可降级、只缓存该缓存的东西。**

##### 三条硬性规则

1. **没有 Redis 时 App 必须完全正常工作。** 检测不到就自动退化为直连数据库，并在设置页显示「缓存：未启用」。
2. **只缓存聚合计算结果，不缓存原始行。** 原始行缓存既无收益又制造一致性风险。
3. **写入即失效。** 任何写 `WorkoutSet` / `MealItem` / `BodyMetric` 的操作，按 key 前缀批量失效。

##### 缓存什么

| 缓存对象 | 为什么这个合理 |
|---|---|
| 本周容量统计（`/api/body-map/volume`） | 要对所有组按肌群映射做聚合，是真正的计算 |
| 进步曲线的 1RM 序列 | 按动作聚合历史，随数据量增长变慢 |
| 肌群 → 动作 索引 | 启动时算一次，之后只读 |
| 食物库搜索结果 | 高频重复查询 |
| 智能体会话上下文 | 天然有 TTL |

##### 技术实现

`CacheService` 接口 + 两个实现：`RedisCacheService`（Redis 可用时）与 `NoOpCacheService`（不可用时）。用 Spring 的条件装配切换，业务代码只依赖接口。

**额外好处**：将来做多人社交版时，排行榜（Sorted Set）、会话、热点数据缓存全部接在同一个 `CacheService` 上，业务代码不用改。

##### 部署形态：Redis 在 VMware 虚拟机里（已确认）

用户已自行部署：**Redis 跑在 VMware 的 Linux 虚拟机里，宿主机经 NAT 网段访问**，日常用 **RESP.app** 查看缓存键。

| 项 | 值 |
|---|---|
| 虚拟机 IP | `192.168.100.128`（取自 VMware DHCP 租约，主机名 `alpaca-VMware-Virtual-Platform`） |
| 网段 | VMware NAT `192.168.100.0/24`，宿主机侧 `192.168.100.1` |
| 端口 | 6379 |
| 客户端 | RESP.app（开发期查键、TTL、内存占用） |

**实测记录（2026-10-14）**：当时虚拟机**未开机**——ping 不通，6379 / 22 / 3306 / 8080 全部关闭。

这条实测恰好证明降级设计不是「可选的优雅」，而是**常态路径**：

> **虚拟机大部分时间是关着的。如果 change 依赖 Redis 才能启动，那它大部分时间都用不了。**

##### 由此产生的四条硬性要求

1. **连接超时必须设短（关键技术细节）**。目标主机不可达时，操作系统层面的 TCP 连接超时可能长达 20 秒；若沿用默认配置，**每次操作都会先卡 20 秒再去查数据库**。
   规定：**连接超时 300 ms，命令超时 500 ms**，超时即视为缓存不可用并走直连。
2. **连续失败后熔断**：一段时间内不再尝试连接（例如 30 秒），避免每次请求都白等 300 ms。
3. **连接参数可配置、可热改**：VM 的 IP 由 DHCP 分配，可能变化。配置放在用户可编辑的文件里，设置页能直接改并测试连通性。
4. **状态可见**：设置页显示「缓存：已连接 192.168.100.128:6379」或「缓存：未启用（连不上 192.168.100.128）」，不静默失败。

##### 开发与测试时怎么处理「Redis 经常不在」

用户已表示：需要联调 Redis 时提前说一声，他会把虚拟机开起来。

**但设计上不应依赖这一点。** 默认的开发与测试路径**不需要 Redis 在线**：

| 场景 | 是否需要 Redis 在线 |
|---|---|
| 日常开发、启动 App | ❌ 不需要，走 `NoOpCacheService` |
| 绝大多数单元测试与集成测试 | ❌ 不需要 |
| 缓存相关集成测试（单独一个测试组） | ✅ 需要，标记 `@Tag("redis")`，手动执行 |
| 验证缓存失效逻辑、用 RESP.app 查看 key 结构 | ✅ 需要 |
| 第一次接通时（确认超时与熔断真的生效） | ✅ 需要 |

**硬性要求：测试套件不得因为 Redis 不在而失败。** 因为「Redis 不在」是常态，测试跟着挂就等于逼迫自己永远开着虚拟机——那这个降级设计就白做了。

需要开机时我会明确说「这一步需要 Redis」，不会让你一直开着。

##### 建议同时做的两件运维小事

- 在 VMware 的 DHCP 里给这台 VM 做**地址保留**（或在 VM 内设静态 IP），免得 IP 漂移后配置失效。
- 给 Redis 设 `requirepass`。NAT 网段默认只在宿主机可见，这一点是安全的；但若改成桥接模式就需要重新评估暴露面。

#### 一句话版本

**现在：SQLite 主库（可切 MySQL profile 练手）+ Redis 作可选缓存（不可用时自动降级）。将来做多用户与社交：MySQL + Redis（排行榜用 Sorted Set）。**

## 五、系统架构

### 分层

```
change.exe（Tauri 2 外壳 / Rust）
  窗口管理 · 启动与关闭后台进程 · 系统托盘 · 开机自启
        │
        ▼
界面（Vue 3 + TS + Vite + Pinia）—— 由系统 WebView2 渲染
  训练打卡 · 饮食记录 · 拍照识别 · 进步曲线 · 智能体对话 · 人体图
        │
        ▼  本地 HTTP · 127.0.0.1 · 随机端口
Java 后台（JDK 25 + Spring Boot 3.x）
  ┌────────────┬────────────┬──────────────────┐
  │  训练模块   │  饮食模块   │ 智能体（LangChain4j）│
  └────────────┴────────────┴──────────────────┘
        │              │                 │
   ┌────▼────┐   ┌─────▼──────┐   ┌──────▼────────┐
   │ SQLite  │   │  图片目录   │   │ 模型接口       │
   │ 单文件   │   │ 本地文件系统 │   │ 唯一出网点·可关 │
   └─────────┘   └────────────┘   └───────────────┘
```

### 启动时序

1. 双击 `change.exe`，外壳先不显示窗口（避免白屏）。
2. 外壳拉起 Java 后台子进程；后台绑定 `127.0.0.1` 的**随机空闲端口**并打印。
3. 外壳读到端口后打开窗口，加载 `http://127.0.0.1:<port>`。
4. 关闭窗口时，外壳先通知后台把数据落盘，再退出。

**端口协商**：由 Java 侧绑定端口 `0` 让操作系统分配，再把实际端口写到标准输出供外壳读取。这样不会与用户机器上的其他服务冲突。

## 六、数据模型

### 三个域，十五张表

**训练域**

| 表 | 关键字段 |
|---|---|
| `Exercise` 动作库 | id · 名称 · 中文名 · 英文名 · 主要肌群 · 器械 · 是否复合 · 默认单位 · 数据来源 id · 归档标记 |
| `WorkoutSession` 一次训练 | id · 日期 · 开始/结束 · 名称 · 主观状态 · 备注 · `source_routine_day_id`（可空，为计划驱动预留） |
| `SessionExercise` 训练中的动作 | id · session_id → · exercise_id → · 顺序 · 备注 · **superset_group**（可空，同值即超级组） |
| `WorkoutSet` 一组 | id · session_exercise_id → · 组号 · **组类型**（normal / warmup / dropset / myo / partial / forced / tut / iso / jump）· 重量 · **次数** · **duration_seconds**（计时动作如平板支撑，与次数二选一）· **per_side**（每侧计数，如弓步）· RIR · 休息秒 · 已完成 · **target_weight · target_reps**（可空） |
| `MuscleGroup` 肌群 | id · 中文名 · 英文名 · 所属部位 · 人体图区域 ids · 建议周容量下限/上限 |
| `ExerciseMuscle` 动作↔肌群 | exercise_id · muscle_group_id · 角色（主要/次要） |

**饮食域**

| 表 | 关键字段 |
|---|---|
| `Food` 食物库 | id · 名称 · 别名 · 数据来源 · **每 100 克**：热量/蛋白/碳水/脂肪/纤维/钠 |
| `FoodPortion` 份量换算 | id · food_id → · 单位名（碗/个/勺/份）· 对应克数 |
| `Meal` 一餐 | id · 日期 · 餐次 · 时间 · 备注 · photo_id（可空） |
| `MealItem` 餐中条目 | id · meal_id → · food_id → · 顺序 · 份量数值 · 份量单位 · **换算克数** · 来源（手动/拍照/智能体） |

**辅助域**

| 表 | 关键字段 |
|---|---|
| `Photo` 照片 | id · 日期 · 相对路径 · 宽 · 高 · SHA-256 · 类型（食物/身材/其他）· 备注 |
| `BodyMetric` 身体数据 | id · 日期 · 指标类型（体重/体脂/各部位围度）· 数值 · 单位 · 备注 |
| `ChatSession` / `ChatMessage` 智能体会话 | session: id · 标题 · 创建时间；message: id · session_id → · 角色 · 内容 · **工具调用记录** · 时间 |
| `ChangeLog` 可回退操作日志 | id · 时间 · 来源（用户/智能体）· 动作（新增/修改）· 目标表 · 目标 id · 改动前（JSON 快照）· 改动后（JSON 快照）· 会话 id · 是否已撤销 |

### 两个建模难点的处理

**难点一：一次训练多动作、每个动作多组** → 三层嵌套（Session → SessionExercise → WorkoutSet）。一个动作行下挂多条组行，几组就是几行。

**难点二：一餐多条目 + 单位换算** → 营养按 per-100g 存，份量单独存。`FoodPortion` 承担「1 碗 = 150 克」这类换算。

### 为什么 `BodyMetric` 用「类型 + 数值」

不给每个围度开一列，是为了**以后加「小腿围」「肩宽」不用改表**。代价是查询时要按类型分组，但这个代价在自用场景里可以忽略。

### 建议周容量从哪来

`MuscleGroup` 上的「建议周容量下限/上限」**是预设值，不是系统算出来的**：初始按常见训练量建议填（大肌群 10–20 组/周、小肌群 6–12 组/周），可以在设置页里逐肌群修改。系统只负责统计实际组数并与这个区间比较，不做任何自动调整。

之所以要把这一点写清楚：这条区间只是**参照系，不是科学结论**。不同来源给出的训练量建议差异很大，让用户自己能改，比内置一套「权威值」更诚实。

## 八、四条主流程

### ① 记录一次训练

`首页：今天还没练` → `点「开始训练」` → `选肌群 → 出动作列表` → `选动作` → `填 60 × 8 · 打勾` → `自动带出上次重量` → `继续下一组…` → `结束训练` → `写入 Session / Exercise / Set`

- 分支：想不起来练什么 → 跳流程 ④
- 约束：填重量时默认值取「该动作上一次的重量」

### ② 记录一餐

`点「记一餐」` → `拍照 / 搜食物 / 外卖截图 / 粘贴订单文本 / 直接说话` → `AI 出条目草稿` → `用户确认或改份量` → `写入 Meal + MealItem` → `热量与宏量营养素实时算出`

四个入口殊途同归，最后都落到同一张条目表，走同一套「草稿 → 确认 → 入库」流程。

- 约束：条目只存「食物 + 份量」，不存绝对热量
- 约束：草稿必须可改——同一张午餐照，三家 App 实测估出 1086 / 845 / 740 千卡

### ③ 智能体改数据

`用户说：中午吃了两个包子一碗粥` → `解析意图` → `调用 create_meal_item ×2` → `写入 MealItem` → `写入 ChangeLog` → `回话：已记入午餐，约 560 kcal`

`用户说：撤销上一步` → `读 ChangeLog` → `回滚到改动前`

- 约束：只允许新增与修改，不允许删除

### ④ 从肌群找动作

`打开人体图` → `肌肉按本周组数着色` → `悬停：股四头肌 · 本周 3 组` → `点击` → `右侧：该肌群动作 + 容量进度` → `+ 加入今天训练` → `回到流程 ①`

## 九、界面与视觉方向

### 布局

左侧分组导航 + 顶部工具条 + 右侧工作区。

```
记录 ── 今日 / 训练记录 / 饮食记录
分析 ── 人体图（预留） / 进步曲线 / 身体数据
助手 ── 智能体对话
────────────────────────
我的 ── 设置 / 关于与致谢      ← 钉在底部
```

「设置」与「关于与致谢」收进底部「我的」分组，用分隔线与功能区隔开——系统级入口不该和日常功能混在一起。

### 视觉：**只做深色主题**（用户已确认）

| 维度 | 规则 |
|---|---|
| 底色 | `#0d0f12`，面板 `#14171b`，分隔用 1px 细线 `#262b31` |
| 强调色 | **唯一的暖红 `#e0453a`** —— 肌肉高亮、主按钮、进度条都用它 |
| 字重 | 标题 800 并压字距（`-0.015em`），正文 400。重量感来自**对比**而非整体加粗 |
| 小标签 | 全大写 + `0.16em` 字距 + `#6b7480` |
| 圆角与阴影 | 圆角 **4–6px**，**不用阴影**，靠描边和间距分层 |
| 留白 | 大幅放宽，用空白而非卡片边框分组 |

**不做浅色主题**：厚重感一半来自深色底与高对比，再维护一套浅色主题会稀释这个方向，且测试成本翻倍。

### 两处刻意的界面设计

1. **「本周容量」放首页最显眼位置**。「腹/核心本周 0 组」这类提醒，只有让人躲不掉才有用。
2. **拍照识别结果页带醒目免责提示**。不是保守，是实测数据支持：同图不同工具差 300+ 千卡。

## 十、错误处理

| 场景 | 处理 |
|---|---|
| 后台进程启动失败 | 外壳显示可读的错误页 + 「查看日志」按钮；不白屏 |
| 端口被占用 | Java 侧绑定端口 `0` 由系统分配，天然规避；若仍失败则重试一次并上报 |
| 模型 API 不可用 / 超时 | 智能体对话降级为只读模式并明确提示；拍照识别退回「手动搜索食物」入口；**不阻塞任何本地记录功能** |
| 数据库迁移失败 | Flyway 启动即校验；失败则拒绝启动并保留上一版本数据文件的备份路径提示 |
| 图片写入失败 | 条目照常入库，照片位置显示占位并标记「待补传」 |
| 智能体改错了数据 | 从 `ChangeLog` 一键回退；界面上每次工具调用都可见、可撤销 |
| 热量计算异常值 | 份量数值设上下限校验；超出范围拒绝入库并提示 |

**核心原则**：**本地记录功能永远不依赖网络。** 模型接口不可用时，打卡、饮食、身体数据必须照常可用。

## 十一、测试策略

自用项目不做全量测试覆盖，但以下四类**必须有**：

| 类型 | 范围 | 工具 |
|---|---|---|
| **单元测试** | 热量与宏量营养素计算、单位换算、周容量统计（主要 +1 / 次要 +0.5）、工具调用参数校验 | JUnit 5 |
| **集成测试** | 数据库迁移、Repository 层、`/api/body-map/volume` 返回值 | Spring Boot Test + 临时 SQLite |
| **契约测试** | 智能体工具的输入输出结构（模型返回的 JSON 必须能被反序列化） | JUnit 5 + 固定样例 |
| **手动验收清单** | 四条主流程各一份 checklist，每次发版前跑一遍 | 人工 |

**特别要测的边界**：

- 份量单位换算：`1 碗 → 150g`、`1 勺 → 15g`、直接填克数三种路径结果一致
- 改份量后热量重算正确（这是「不存绝对热量」这条约束的验收点）
- `ChangeLog` 回退能把数据恢复到改动前的精确状态
- 动作名匹配（free-exercise-db ↔ hasaneyldrm）的命中率与未命中清单
