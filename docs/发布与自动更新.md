# 发布一个版本（自动更新是怎么转起来的）

> 2026-10-25 更新为「两份清单」。上一版写的是「GitHub 单源 + gh CLI」，与当时现实不符：
> 下载源已切到阿里云 OSS，而 `gh` 在这台机器上装不上（winget 的 CDN 被挡）。

---

## 一、现状

```
你（开发者）                阿里云 OSS（主）              用户的应用
     │                          │                          │
     │  构建 + 签名              │                          │
     ├── latest.json ──────────► │ ◄──── 检查更新（优先） ────┤
     ├── *.exe ────────────────► │ ◄──── 下载 106 MB ───────┤
     └── *.exe.sig ────────────► │        验签 → 安装 → 重启 │
                                  │
                    GitHub（兜底，只有 714 B 的 latest.json）
```

**为什么 OSS 优先：** GitHub 的 release 文件在国内约 320 KB/s，106 MB 要 5-6 分钟；
阿里云几秒。所以 `endpoints` 是一个数组，Tauri 按顺序试：

1. `https://change-release.oss-cn-beijing.aliyuncs.com/latest.json`
2. `https://github.com/alpaca-cn/changE/releases/latest/download/latest.json`

**GitHub 上只放 latest.json（714 字节）**，它的 `url` 指向 OSS。这样：

- 老版本（只认 GitHub）也能发现新版
- 真正的 106 MB 从 OSS 下

### 三样东西各在哪

| 东西 | 位置 | 是不是秘密 |
|---|---|---|
| 公钥 | `tauri.conf.json` 的 `plugins.updater.pubkey` | 不是 |
| 私钥 | `keys/changE-updater.key`（已 gitignore） | **是** |
| 清单地址 | `tauri.conf.json` 的 `endpoints` | 不是 |

## 二、发一个版本

### 1. 升版本号（两处必须一致）

```
frontend/package.json               "version"
frontend/src-tauri/tauri.conf.json  "version"
```

**必须比用户手上那个高。** 同一个版本号重复发，更新器会说「已是最新」，
而那种「没反应」会被误判成更新器坏了。

### 2. 构建

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = Get-Content keys/changE-updater.key -Raw
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = ''

cd backend
mvn -B -q clean -DskipTests package
Copy-Item target/change-backend-*.jar ../frontend/src-tauri/resources/change-backend.jar -Force

cd ../frontend
pnpm tauri build
```

> `clean` 是必要的：不 clean 时 `target` 里会同时留着旧版本的 jar，
> 按文件名排序很可能取到旧的那个（2026-10-22 真发生过）。

### 3. 整理发版文件

```powershell
python scripts/prepare-release.py
```

产出到 `artifacts/release/`：

```
changE_<ver>_x64-setup.exe        106.9 MB
changE_<ver>_x64-setup.exe.sig    436 B
latest.json                       714 B   （url 指向 OSS）
```

脚本会自检：`.sig` 与 `latest.json` 里的 `signature` **逐字节一致**、无 BOM。

### 4. 上传到 OSS

控制台 → Bucket 列表 → `change-release` → 文件列表 → 上传文件。

**三个都传，目标目录留空（根目录），文件名一个字符都不能改** ——
`latest.json` 里的 URL 是写死的。

### 5. 在 GitHub 建 release（只放 latest.json）

https://github.com/alpaca-cn/changE/releases/new

- Tag：`v<ver>`，Create new tag on publish，Target `main`
- 附件：**只拖 `latest.json`**（714 B）
- 必须 Publish，**不能是 Draft**（draft 不在 `releases/latest` 里）

### 6. 验证

```powershell
$b = 'https://change-release.oss-cn-beijing.aliyuncs.com'
foreach ($f in 'latest.json', 'changE_<ver>_x64-setup.exe.sig', 'changE_<ver>_x64-setup.exe') {
  $r = Invoke-WebRequest "$b/$f" -Method Head
  "$f  $($r.StatusCode)  $($r.Headers['Content-Length'])"
}
```

三个都 200 且大小与本地一致，就通了。然后回应用里点「检查更新」。

## 三、失败对照表

| 现象 | 原因 |
|---|---|
| `AccessDenied` / `The bucket you access does not belong to you` | bucket 不是公共读，或「阻止公共访问」没关 |
| `NoSuchKey` | 文件传到了子目录里，或文件名不一致 |
| **界面一直转圈** | 网络被挡（VPN / 代理）。0.2.3 起有 15 秒超时会明说 |
| `404` / `Could not fetch` | GitHub release 存成了 draft，或者没附 latest.json |
| 「签名不匹配」 | `.sig` 与 `latest.json` 里的 signature 不一致（多半漏传了 `.sig`） |
| 「已是最新」 | 版本号没升，或 tag 不是最新发布的那个 |

## 四、三个踩过的坑

1. **PowerShell 5.1 对无 BOM 的 `.ps1` 按 ANSI 解码** —— 中文变乱码，且乱码里的
   字符会破坏语法（报的错是「`&&` 不是合法的语句分隔符」，与真实原因毫无关系）。
   脚本要存成 UTF-8 with BOM。

2. **`tauri signer generate -p ""` 会被 PowerShell 吞掉**（空字符串不传给原生命令）。
   要用 `--password=` 的等号形式。

3. **安装时如果应用还在跑**，NSIS 会报 `Error opening file for writing:
   <安装目录>\runtime\bin\java.dll` —— `java.dll` 被正在运行的后端占用。
   先关掉应用（或杀掉 `changE` / `java` 进程）再重试。

## 五、还没解决的

- **每次更新都下全量 106 MB**：Tauri 的 NSIS 更新没有差分。真要省流量得换
  MSI + 差分方案，成本远大于收益。
- **上传 106 MB 走你的上行带宽**：这一步帮不了，除非给 OSS 配同步工具 + AccessKey。
