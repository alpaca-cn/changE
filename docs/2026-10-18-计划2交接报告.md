## 三、⚠️ 工具陷阱（本报告最重要的部分）

这些坑在这个项目里**实际发生过**，每一条都毁过东西或差点得出错误结论。

### 1. 绝不用 PowerShell 做文本往返

PS 5.1 的 `Get-Content` / `Set-Content` **不带 `-Encoding` 时按 ANSI(GBK) 读 UTF-8**，写回即成双重编码，**有损且不报错**。

- 本项目毁过一份 15 万字节的中文计划文档（174,919 字节全变乱码）
- **写文件**：用编辑器工具（`write` / `edit`），或 Python 且显式 `encoding='utf-8'`、`newline='\n'`，或直接 `read_bytes` / `write_bytes`
- **读文件**：用 `read` 工具，或 Python

### 2. `Get-Content` 会把好文件显示成乱码，让你得出错误结论

**这个坑在本轮又踩了一次**：重新生成迁移后我看了眼文件头，看到 `-- V7: 17 鍧楄倢缇ょ殑绉嶅瓙鏁版嵁銆?`，差点以为生成器写坏了编码。用 Python 按字节核实后完全正常（`U+FFFD` 为 0）。

**规则**：凡是「看一眼文件内容」的判断，一律用 Python 读字节 + 显式 UTF-8 解码，**不要信 PowerShell 的显示**。此前也出过一次 `Get-Content` 给出假阴性、导致我误判某个校验已生效。

### 3. 绝不用 `java -cp target/classes` 探行为

会读到陈旧的 class。**一律 `mvn -B clean test`**（`clean` 不能省——Windows 的时间戳粒度会让增量编译跳过重编）。

### 4. 变异测试的还原方式：字节级备份，不要 `git checkout --`

本轮实施者的第一版变异脚本用 `str.replace(new, old)` 还原，**空字符串 `new` 会在位置 0 匹配**，把代码插到文件开头。更糟的是 `git checkout -- <file>` 把**尚未提交的新代码**一起冲掉了。

**正确做法**：变异前 `read_bytes()` 备份到内存，还原时 `write_bytes()` 回来，然后比 sha256。

### 5. 计划里的代码 fence 与磁盘必须逐字一致

项目的元约定。但**本计划的 fence 现在与磁盘并不一致**（见第七节「已知不一致」），做 Task 3 时**不要盲目照抄 fence**——以磁盘上已通过的代码风格为准，改完把 fence 同步过来。

### 6. 其它

- PowerShell 里 `git rev-parse foo^{commit}` 的 `^{...}` 会被吃掉，用 `git rev-list -n 1 <tag>` 代替
- PowerShell heredoc（`<<'EOF'`）不支持；用 `Set-Content` 写临时文件再 `git commit -F <文件>`（且那个文件本身要经 Python 归一化成 UTF-8 无 BOM + LF）
- 中文提交信息走 `git commit -F <文件>`，文件经 Python 写
